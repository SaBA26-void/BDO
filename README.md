# ნორთსტარ სერვისეზი — შვებულებების MCP სერვერი და ქართული HR ასისტენტი

პროექტი ორი ნაწილისგან შედგება:

1. **MCP სერვერი** (`mcp_server/`) — შვებულებების მართვის ხელსაწყოები SQLite ბაზაზე, როლების გამიჯვნით
   (თანამშრომლის ასისტენტი / HR).
2. **ქართული CLI ასისტენტი** (`src/cli.py`) — ესაუბრება თანამშრომელს, პოლიტიკის კითხვებს პასუხობს RAG-ით,
   ხოლო ბალანსსა და შვებულების მოთხოვნას MCP სერვერის მეშვეობით ამუშავებს.

## დაყენება

საჭიროა Python 3.12+ (პროექტი შემოწმებულია 3.14-ზე).

```bash
pipenv install --dev          # ან: pip install -r requirements.txt
cp .env.example .env          # და ჩაწერეთ GEMINI_API_KEY
```

`GEMINI_API_KEY` საჭიროა მხოლოდ პოლიტიკის კითხვებისთვის (embedding-ები და პასუხის გენერაცია Gemini-ის
OpenAI-თავსებადი endpoint-ით). ბალანსი და მოთხოვნები გასაღების გარეშეც მუშაობს.

განმავლობაში ერთ სესიას იყენებს. სერვერის ლოგი იწერება `data/mcp_server.log`-ში.

## მონაცემთა ბაზა

არჩეულია **SQLite** (SQLAlchemy ORM-ით): ფაილური ბაზაა, სერვერს არ საჭიროებს და დავალების მოცულობისთვის
საკმარისია. ORM-ის გამო PostgreSQL-ზე გადასვლა მხოლოდ connection string-ის შეცვლას მოითხოვს.

| ცხრილი | შინაარსი |
|---|---|
| `employees` | თანამშრომელი, დეპარტამენტი, გამოსაცდელი ვადის დასასრული, ხელმძღვანელი |
| `leave_types` | შვებულების სახე, დღის ერთეული (სამუშაო/კალენდარული), წლიური ლიმიტი, ასისტენტით ხელმისაწვდომობა |
| `leave_requests` | თანამშრომელი, სახე, თარიღები, დღეები, სტატუსი, `created_at`, `created_via`, განმხილველი |
| `leave_entitlements` | თანამშრომლის წლიური ლიმიტი/ნაშთი სახეების მიხედვით: კუთვნილი, გადმოტანილი, გამოყენებული, განხილვაში, დარჩენილი |
| `public_holidays` | უქმე დღეები სამუშაო დღეების დასათვლელად |

ბალანსი მუხლი 5.1-ის მიხედვით აისახება: ახალი მოთხოვნა `pending_days`-ს ზრდის და `remaining_days`-ს ამცირებს,
დამტკიცება გადააქვს `used_days`-ში, უარყოფა ან გაუქმება აბრუნებს ნაშთს.

## MCP ხელსაწყოები და როლები

ყველა ხელსაწყო, რომელიც თანამშრომლის მონაცემებს ეხება, იღებს `caller_id`-სა და `caller_role`-ს
(`employee` ან `hr`). სერვერი ამოწმებს, რომ `caller_id` აქტიური თანამშრომელია, ხოლო `hr` როლი მხოლოდ
HR დეპარტამენტის (`HRS`) თანამშრომლებს შეუძლიათ.

| ხელსაწყო | `employee` (თანამშრომლის ასისტენტი) | `hr` |
|---|---|---|
| `create_leave_request` | მხოლოდ საკუთარი ANNUAL/SICK/UNPAID, მუხლი 12.3-ის ყველა შემოწმებით; `created_via = assistant` | ნებისმიერი სახე, ნებისმიერი თანამშრომლისთვის; `created_via = hr` |
| `list_leave_requests` | მხოლოდ საკუთარი მოთხოვნები | ყველა; ფილტრები: თანამშრომელი, სტატუსი, თარიღების დიაპაზონი (გადაფარვით) |
| `get_leave_balance` | მხოლოდ საკუთარი | ნებისმიერი თანამშრომლის; წელი და სახე სურვილისამებრ |
| `approve_or_reject_leave_request` | აკრძალულია (მუხლი 12.3) | დაშვებულია, საკუთარი მოთხოვნის გარდა |
| `cancel_leave_request` | აკრძალულია (მუხლი 12.3) | დაშვებულია |
| `list_leave_types` | საჯარო საცნობარო მონაცემი, `caller` არ სჭირდება | |

ასისტენტის მიერ შექმნილ მოთხოვნაზე სერვერი ამოწმებს: მიმდინარე წელს (12.3), თარიღების გადაფარვას (12.3),
გამოსაცდელ ვადას (4.3), წინასწარ შეტყობინებას (4.4, 7.2), უწყვეტ მაქსიმუმს (4.5), აუდიტის შეზღუდულ
პერიოდებს (4.6), ბალანსს (5.1, 6.4) და უხელფასო შვებულების წლიურ ლიმიტს (7.1). უარის შემთხვევაში პასუხში
ბრუნდება მიზეზი და მუხლის ნომერი; უფლებამოსილების დარღვევისას დამატებით `"forbidden": true`.

**შეზღუდვა:** `caller_id` და `caller_role` კლიენტი გადმოსცემს. ლოკალური stdio სერვერისთვის ეს საკმარისია
(CLI თავად უშვებს სერვერს და ყოველთვის `employee` როლს იყენებს), თუმცა საწარმოო გარემოში აბონენტის ვინაობა
ავთენტიფიკაციიდან (მაგ. HTTP ტრანსპორტზე OAuth ტოკენიდან) უნდა განისაზღვროს და არა არგუმენტიდან.

## RAG

- **წაკითხვა:** DOCX — `python-docx`-ით, აბზაცები და ცხრილები დოკუმენტის თანმიმდევრობით; PDF — `pypdf`-ით
  (OCR არ სჭირდება). PDF-ის გვერდის ზედა და ქვედა კოლონტიტულები (კომპანია/დოკუმენტის კოდი/გვერდის ნომერი)
  იშლება.
- **დაყოფა მუხლებად:** DOCX-ში სათაურებს `Heading 1/2` სტილები განსაზღვრავს; PDF-ში დანომრილი სტრიქონი
  (`4.` / `4.4 …`) სათაურად ითვლება მხოლოდ მაშინ, თუ ნუმერაციის თანმიმდევრობას აგრძელებს — ასე ცხრილის
  უჯრები („200 ლარი“, „31 მარტამდე“) სათაურად არ აღიქმება. თითოეული ფრაგმენტი ერთი ქვემუხლია და იწყება
  დოკუმენტის სათაურითა და მუხლის გზით (მაგ. `4. ყოველწლიური … > 4.4 მოთხოვნის წარდგენა …`); გრძელი მუხლი
  ~1000 სიმბოლოიან ნაწილებად იყოფა გადაფარვით.
- **ძიება:** Gemini embedding-ები (768 განზომილება) და cosine similarity; ვექტორები ინახება
  `data/embeddings_cache.json`-ში, ამიტომ დოკუმენტები ხელახლა მხოლოდ ცვლილებისას იტვირთება.
- **წყაროების პრიორიტეტი:** მოქმედი პოლიტიკები (შვებულების პოლიტიკა v4.0 — 100, სხვა მოქმედი პოლიტიკები — 90)
  უსწრებს FAQ-ს (40) და მოძველებულ სახელმძღვანელოს (10). მოძიებული ფრაგმენტები LLM-ს პრიორიტეტის მიხედვით
  მიეწოდება და ინსტრუქცია მოითხოვს წინააღმდეგობისას უფრო მაღალი პრიორიტეტის წყაროს გამოყენებას.
- **პასუხი:** ეყრდნობა მხოლოდ მოძიებულ კონტექსტს და მთავრდება წყაროთი და მუხლით, მაგ.
  `[წყარო: Leave_and_Absence_Policy_v4.0.docx, მუხლი 4.4]`. თუ ინფორმაცია ვერ მოიძებნა, ასისტენტი ამას
  პირდაპირ ამბობს.

## ასისტენტის ლოგიკა

`src/assistant/intents.py` ყოველ შეტყობინებას ერთ-ერთ განზრახვად აკლასიფიცირებს, `agent.py` კი ამარშრუტებს:

- `CHECK_BALANCE` — „ბალანსი“, „დამრჩა“ და მსგავსი → `get_leave_balance`;
- `CREATE_LEAVE_REQUEST` — მოთხოვნის გამომხატველი ფრაზა ან „შვებულება“ + თარიღი → სახის ამოცნობა
  (ANNUAL/SICK/UNPAID/BEREAVEMENT/STUDY/PARENTAL), `dry_run`-ით გადამოწმება, თანამშრომლისთვის სახის,
  თარიღებისა და დღეების ჩვენება და მხოლოდ „კი“/„დიახ“-ის შემდეგ შექმნა (მუხლი 12.2). გლოვის, სასწავლო და
  მშობლის შვებულებისას ასისტენტი წესებს განმარტავს და HR-თან გადაამისამართებს;
- `POLICY_QA` — დანარჩენი, მათ შორის თარიღის გარეშე დასმული კითხვები → RAG.

თარიღები მიიღება `YYYY-MM-DD` ფორმატით.
